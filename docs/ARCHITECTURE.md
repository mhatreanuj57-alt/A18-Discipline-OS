# Architecture

`MainActivity` hosts native Compose screens. `DisciplineViewModel` exposes Room observations and DataStore preferences as StateFlows, executes repository actions on Dispatchers.IO, and surfaces errors without resetting user data. Compose uses lifecycle-aware collection. No browser or website runtime is embedded.

Startup uses a themed Android starting window (platform splash attributes on API
31+) followed by `LaunchScreen` while initialization or the first snapshot is
pending. The ViewModel's initialized flag is set only after repository setup
succeeds. Retry reruns setup and restarts the snapshot observation, retaining all
records. Permissions are requested after initialization. Fresh navigation starts
at To-do list; saved navigation survives configuration changes and backgrounding.

`data/Models.kt` defines typed, serializable models matching the website's backup format and validates imports at the boundary. `Repository` is the shared write boundary for task/schedule synchronization, completion history, recurrence materialization, plan initialization, timer completion and backup merges. Multi-record operations use Room transactions. Recurrence generates deterministic future IDs and clears completed state. A single persistent seed marker prevents duplicate plan creation and respects deliberate task deletion.

Room's `entries` table has composite `(kind,id)` keys and a `(kind,date)` index. Typed record payloads retain the portable version-1 JSON format without lossy field conversion. Non-sensitive dates are queryable; sensitive payloads and dates are encrypted. Room's exported schema is version-controlled. There is no destructive fallback. For a future database schema version, implement a migration, test it from every supported version and retain schema snapshots. For a record-format change, add defaults or a payload migration before changing the decoder; never silently discard failed records.

Settings live in Preferences DataStore. The active timer is in Room with a stable session ID and an absolute end timestamp. Both the foreground UI and a background WorkManager job can finalize it; the Room transaction and deterministic log ID prevent double counting. Task completion stays a separate explicit user action. No foreground service is necessary to keep a countdown accurate, but background notification delivery is subject to Android scheduling limits.

`PrivateVault` generates/reuses an Android Keystore AES key. Each AES-GCM record has a fresh IV and authenticated kind/ID. Sensitive content never enters the public Snapshot. Journals/private records are decrypted only when explicitly read or consented to for export. Decryption failure reports an error; the key or data is not replaced as a recovery shortcut. `BackupCrypto` uses portable password encryption rather than exporting device-bound Keystore material.

Backup readers are bounded to 50 MB, deserialize/validate before transaction, and preserve existing edited IDs. Private information requires explicit consent in both directions. Ordinary exports do not read/decrypt private records. Unknown JSON keys are ignored for forward tolerance; recognized web drafts are kept as opaque bounded JSON, with sensitive drafts encrypted. The application has no internet permission and no telemetry SDK.

The static plan is bundled in `app/src/main/assets/plan.json`, with no website or Node.js dependency. It was prepared from the original academic curriculum and college timetable. Native evening tasks use deterministic `evening-v1` IDs and linked `evening-slot-v1` schedule IDs. All 123 dates are included, with two tasks on 19 October and seven daily thereafter. Starts, endings and explicit check-ins are computed by the native notification engine. To edit bundled defaults, update this validated JSON asset and its coverage tests; saved user edits are retained by repository conflict rules.

The transactional `evening-plan-v1` migration archives existing in-range tasks and non-college blocks before inserting the new plan. Payloads and histories remain intact. Archived tasks are visible under Previous plan, cannot generate recurring instances or notifications, and retain recorded outcomes in analytics. Backups include archives and extra alerts; restoring old `plan-v1` records in the plan range archives them instead of reviving duplicate daily responsibilities. Defaulted JSON fields preserve decoding of older backups without changing the Room schema.

`plannedAlerts` computes future task starts, endings and explicit follow-ups in the device timezone, excluding archived and terminal tasks. An end at or before the start belongs to the next date. AlarmManager holds a rolling eight-day window. A Preferences DataStore registry records each JSON-pair alert key and timestamp; a mutex serializes reconciliation and consumes each delivered alert once. User notifications use `setExactAndAllowWhileIdle` with special scheduling access; denied access falls back to inexact idle-allowed scheduling. There is no `setAlarmClock`, alarm-clock screen, full-screen intent or next-alarm indicator. Deep idle quotas can delay closely spaced deliveries. An inexact midnight alarm refreshes the window. Boot, package replacement, timezone and clock changes rebuild alarms. Old WorkManager task jobs are canceled on upgrade. Notifications use separate high-importance start/end channels with stable `android.resource` sound URIs pointing to the user's bundled WAV/MP3. Generic lock-screen public versions protect previews; only public task fields are read. Focus completion retains its existing WorkManager path. Android controls sound arbitration when two notifications arrive simultaneously.

Version 1.0.2 starts the plan on 19 October. `retired-weekend-v1.json` stores the exact former defaults for 17–18 October solely for a transactional cleanup. Exact unmodified defaults can be removed; edited records, linked schedules, activity references and outcomes are preserved. A marker makes this cleanup idempotent. Restore uses the same comparison so old backups do not revive unused defaults or discard user edits.
